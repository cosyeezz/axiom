# Axiom 通用工具构造方案

- 日期：2026-09-24
- 状态：讨论设计稿，供审阅和继续细化；不是已实施能力说明。
- 范围：将 Axiom 自有能力收拢到固定的模型工具入口，明确常驻说明、按需发现、调用与后台职责。
- 关联文档：[按需记忆咨询与专用 Pi 检索讨论共识](Axiom-memory-query-discussion-2026-09-24.md)。
- 本次仅整理讨论，不查阅或修改实现代码。下文动作名称、参数和返回示例均为设计示意，不代表现有接口。

## 1. 目标与核心决定

随着 Todo、委派、记忆、skill、MCP 等能力增加，不再为每项 Axiom 能力向模型注册独立、完整的工具 schema。

核心方向：

> 模型只注册一个 Axiom 通用工具；系统提示词只放常用动作的简短使用说明；其他能力及其说明按需查询；Axiom 负责参数校验、权限检查、执行分发与任务生命周期。

具体目标：

- 控制常驻工具定义和系统提示词的体积。
- 常用动作直接调用，不增加不必要的发现步骤。
- 低频动作连目录都不常驻，需要时根据任务描述发现。
- 不因新增低频能力而修改模型侧工具 schema 或追加常驻说明。
- 尽量保持长会话的工具定义与系统提示词前缀稳定。

“一个工具”首先指 Axiom 自有能力的模型入口。文件读取、编辑、命令执行等基础工具是否一并迁移，尚未确定，不作为本稿前提。

## 2. 整体结构

```text
主模型
  ├─ 系统提示词
  │    基本边界 + 通用入口约定 + 常用动作简短说明
  │
  └─ axiom（唯一的 Axiom 工具）
       ├─ capability.find：查找能力
       ├─ capability.describe：取得调用说明
       └─ 业务动作：委派、Todo、记忆等
                      ↓
                 Axiom 后台
       能力登记 → 校验/确认 → 执行 → 结果或状态
```

查找能力、获取说明同样通过 `axiom` 调用，不额外注册模型工具。

收拢的是模型可见入口，不是取消内部能力、校验或权限。通用入口不能变成绕过受管操作的任意脚本通道。

## 3. 通用工具外层契约

建议工具名为 `axiom`，外层只包含两个必要字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `action` | 字符串 | 动作标识，例如 `delegate.start` |
| `arguments` | 对象 | 对应动作的参数 |

概念上的外层 schema：

```json
{
  "type": "object",
  "properties": {
    "action": { "type": "string" },
    "arguments": { "type": "object" }
  },
  "required": ["action", "arguments"],
  "additionalProperties": false
}
```

该示例用于说明结构，不代表所有模型提供方严格模式都支持这种动态参数对象。实际适配需后续确认；不得声称启用外层严格模式即可约束每个业务动作的内部参数。

不在外层放入全部动作的 `enum` 或各动作完整参数的 `oneOf`。否则只是把多份大 schema 包成一份大 schema，无法达到精简目的。

### 最小工具描述

> 使用 action 指定 Axiom 动作，arguments 提供参数。已知动作及参数要求时直接执行；不知道适用能力时调用 capability.find；需要具体参数说明时调用 capability.describe。

真实字段与工具名称仍可在后续讨论中调整。

## 4. 系统提示词：仅常用动作常驻

系统提示词保留：

1. 基本职责、指令优先级、权限、安全及如实报告等不可移除的边界。
2. 通用工具使用原则及两个发现动作的最小说明。
3. 人工选择的一小组常用动作及其常见调用方式。

低频能力不放全量名称、不放目录、不放简介，也不放参数定义。

### 使用原则示意

> 通过 axiom 调用 Axiom 能力。已知动作及参数要求时直接执行；不知道有哪些适用能力时查找能力；知道动作但不清楚参数时获取说明。已取得且仍适用的说明直接沿用，不重复查询，不猜测动作名称和必要参数。

### 常用动作说明示意

```text
capability.find：按需要查找能力，参数 query。
capability.describe：获取具体动作说明，参数 action。

delegate.start：启动子任务，参数 task、context，返回 taskId。
delegate.append：补充指令，参数 taskId、message。
delegate.result：完成通知后读取结果，参数 taskId。
delegate.cancel：请求停止，参数 taskId，可选 reason。
```

上述委派动作仅展示说明形式，不表示常驻清单已经选定，也不要求原有委派语义被简化为这些字段。

常用动作也经通用工具执行，不再另行注册原生 schema。复杂选项与少见用法可留在按需说明中。具体常驻清单及长度预算待定，一期不做自动升降级。

## 5. 低频能力的发现与说明

### 5.1 capability.find：按需要发现

模型不必先猜中动作名称，可以描述目标：

```json
{
  "action": "capability.find",
  "arguments": {
    "query": "查看和重新连接 MCP 服务"
  }
}
```

返回少量相关候选，例如：

```text
mcp.list：查看服务及连接状态。
mcp.reconnect：请求重新连接指定服务。
```

- 返回候选来自当前真实可用能力，不编造动作。
- 不将全量目录倾倒进主会话；候选数量和摘要预算待定。
- 找不到时明确说明未匹配到能力。
- 查找只是发现，不因意图相似而直接执行有副作用的动作。
- 一期可先基于登记的名称、用途和关键词匹配，不必新增模型路由或接入 Jev/Laya；匹配算法尚未定案。

### 5.2 capability.describe：取得准确的调用说明

```json
{
  "action": "capability.describe",
  "arguments": {
    "action": "mcp.reconnect"
  }
}
```

建议返回：

- 用途及适用场景。
- 必要参数、可选参数和合法取值。
- 一个最小合法示例。
- 返回结果或异步状态的说明。
- 重要限制、必要确认和副作用。

模型需要的是足够准确的使用说明，不要求每次返回完整 JSON Schema。简单参数用简短文字即可，复杂参数可用结构化定义。

如果 `find` 已返回足够调用的信息，可直接执行，不强制先 `find` 再 `describe`。已知动作但不熟悉参数时，也可直接 `describe`。

## 6. 后台动作定义与执行

每个动作在后台应具有足够的登记信息：

| 内容 | 用途 |
|---|---|
| 动作标识、用途、检索关键词 | 能力发现 |
| 参数要求、调用示例、结果说明 | 生成准确的使用说明 |
| 校验逻辑及处理函数 | 验证并执行 |
| 权限、必要确认与生命周期属性 | 保持受管执行边界 |

这描述的是所需信息，不要求一期建设通用插件平台或复杂注册框架。

调用说明应与执行契约具有共同的权威来源，避免手写两套定义逐渐不一致。究竟采用内部 schema、程序定义还是其他结构，待实施前确定。

执行路径：

```text
收到 action 与 arguments
          ↓
查找动作 → 校验参数和前置条件
          ↓
检查权限及必要确认
          ↓
调用对应内部能力
          ↓
返回结果、状态或明确错误
```

### 错误处理原则

- 未知动作：不猜测执行，提示通过发现入口查找。
- 参数不合法：指出字段及要求；校验阶段不产生业务副作用。
- 缺少业务信息：明确缺项，不为通过校验擅自选择授权或目标。
- 需要确认：沿用对应能力的确认机制，不以通用入口替代确认。
- 执行失败：区分未执行、已执行失败及结果未知；结果未知时先查状态，不盲目重试。

外层 schema 与后台校验并不能保证模型首次生成正确业务参数。后台拒绝非法调用与模型侧强结构约束不是同一件事。

## 7. 委派示例：多个操作，一个入口

以下仅说明如何收拢调用，不冻结实际委派接口。

### 启动

```json
{
  "action": "delegate.start",
  "arguments": {
    "task": "分析两个方案的差异，返回建议及依据",
    "context": "只读分析，不修改文件，重点比较维护成本"
  }
}
```

启动被接受后可返回：

```json
{
  "taskId": "task-17",
  "status": "running"
}
```

任务接受不代表已经完成。预算、上下文隔离和启动细节仍由后台管理。

### 补充指令

```json
{
  "action": "delegate.append",
  "arguments": {
    "taskId": "task-17",
    "message": "额外比较对长会话缓存的影响"
  }
}
```

任务已结束时需如实说明。如何区分调整当前工作与排队续接，应保留对应能力的真实语义，不在本稿擅自确定。

### 获取结果

```json
{
  "action": "delegate.result",
  "arguments": { "taskId": "task-17" }
}
```

完成通知由 Axiom 提供，通知后按需读取结果，不要求主模型轮询。尚未完成时只返回真实状态，不能把任务标识包装成已完成结果。

### 取消

```json
{
  "action": "delegate.cancel",
  "arguments": {
    "taskId": "task-17",
    "reason": "用户已调整方向"
  }
}
```

取消请求被接受、正在停止、已停止需要区分；取消不等于撤销已产生的副作用。

## 8. 记忆、skill 和 Todo 的关系

### 记忆查询

主代理调用 `memory.query` 一类动作，提供问题及必要背景；Axiom 启动专用记忆 Pi，检索细节保留在该代理系统提示词中，主代理取得精简参考和来源。

```json
{
  "action": "memory.query",
  "arguments": {
    "query": "本次交付应遵循什么汇报要求？",
    "context": "用户本次明确要求不画图"
  }
}
```

记忆查询是历史要求与经验检索；能力发现查询的是当前真实可用动作与调用规范。不能用旧记忆代替权威接口说明。

### skill

skill 承载方法和流程，可通过动作按需发现、读取或交由执行者使用。skill 本身不是新增授权，也不等于运行时工具能力。详细内容无需全部常驻。

### Todo

Todo 维护可通过内部动作执行，但原有目标确认、状态及验收约束不因入口收拢而改变。Todo 不承担能力查询或记忆预取的调度职责。

## 9. 前缀缓存与可靠性的取舍

工具 schema 通常通过请求的工具定义提供，不一定属于系统提示词正文，但同样会占据上下文。

- 固定通用工具和稳定常驻说明，避免频繁改变前部定义。
- 按需说明作为工具结果追加到当前消息链中，不要求动态注册目标工具。
- 这些结果仍占上下文，不是零成本；后台或模型侧缓存的实际收益需验证。
- 不宣称所有服务的前缀缓存机制相同，也不保证该设计必然命中缓存。

原生工具注册通常更有利于参数生成；提供方支持的严格模式还可能约束结构。返回说明主要依赖模型理解，通用外层不自动约束目标动作的动态参数。

本方向选择以稳定入口、简短准确说明及后台校验换取较小常驻负担，不将其说成与原生严格 schema 等价。若后续实际参数错误率不可接受，再评估改进，不预设动态注册是默认答案。

## 10. 一期边界

一期建议聚焦：

- 一个固定 Axiom 通用工具。
- 常用动作简短说明。
- 按需能力发现和调用说明。
- 后台校验、权限与实际分发。
- 保留现有能力所需的通知和生命周期语义。

暂不作为一期前提：

- 动态增删模型侧原生工具 schema。
- 自动升降级常驻动作。
- 完整工具目录或完整参数 schema 常驻。
- Todo 单元绑定查询、全量预取、复杂缓存。
- 自然语言意图直接推断并执行有副作用的动作。
- Jev/Laya 或额外模型路由平台。
- 自动将全部能力改造成可修改脚本。

## 11. 建议验证场景

这些是后续实现的验证建议，不是已通过的测试：

1. 常用动作直接执行，无须先查找说明。
2. 模型不知道名称时，可按任务描述发现低频能力并正确使用。
3. 未知动作和缺失参数被明确拒绝，未产生业务副作用。
4. 委派的启动、补充、通知、结果读取和取消语义保持完整。
5. Todo 等动作的必要用户确认不能绕过。
6. 添加低频能力后，模型侧通用 schema 和常驻说明不必改变。
7. 常驻说明与实际执行契约一致，按需返回有长度控制。
8. 对照原生工具方式观察参数重试、上下文体积、延迟及缓存表现，不虚构收益。

## 12. 待确认事项

- 常驻动作的具体清单及说明长度。
- Axiom 通用入口是否扩展到基础文件与命令工具。
- `action`、`arguments` 等最终字段和提供方适配方式。
- 能力发现的匹配方式、候选数量及无命中体验。
- 动作定义与常驻说明如何同步，何时允许更新会话提示词。
- 返回结果与错误是否采用统一外层结构。
- 异步任务的最终标识、通知与结果获取契约。
- 如何在不增加复杂机制的前提下减少参数重复错误。

## 13. 结论

> 常用动作的说明放在系统提示词，其他能力不常驻；模型通过一个稳定的 axiom 工具发现、了解并执行动作，具体校验与执行由 Axiom 负责。

本稿固化构造方向并提供示例，不代表任何工具已经迁移，也不修改运行时行为。
