# Axiom 按需记忆咨询与专用 Pi 检索：讨论共识

- 日期：2026-09-24
- 状态：讨论记录，供继续细化；不是已实施功能说明或完整实现规格。
- 范围：固化本轮关于主会话精简、查询时机、skill 放置位置及一期检索路径的共识，不涉及代码实现。
- 背景材料：此前讨论基于 `docs/Axiom-memory-Laya-Jev-Pi-implementation-2026-09-23.md`。该名称仅标识讨论来源；本记录独立阅读，不要求原文件已纳入版本控制。本记录不覆盖或修改原方案。

## 1. 要解决的问题

随着 harness 增加委派、Todo、skill、MCP 等能力，常驻工具说明、工作规则、用户偏好和历史经验可能持续膨胀。某些要求只有特定时刻才用到，例如长程任务交付时的表达风格；用户还可能在执行过程中纠正这些要求。

目标不是单纯把多个工具改名为一个，而是：

- 主会话不必一直携带所有做法和细则。
- 需要历史要求或经验时，能够按当前问题取得适用参考。
- 检索、筛选和试错过程留在独立上下文，不全部回流主会话。
- 具体规则接近使用时机加载，及时体现本次任务中的明确要求和纠正。

统一入口可以隐藏内部能力增长，但不等于底层执行能力消失。脚本或 skill 可以组织调用，不能凭文字产生运行时能力或扩大授权。本期不以“把所有 harness 工具统一成一个工具”为交付前提。

## 2. 当前共识：主代理咨询，记忆代理检索

主代理系统提示词规定何时、如何请求记忆；详细检索流程放在记忆代理内部。

```text
主代理
  判断当前需要哪些历史要求或经验
  提交问题及必要背景
          ↓
独立的记忆查询 Pi
  理解问题 → 查索引 → 读相关内容 → 判断适用性 → 整理
          ↓
主代理
  接收精简参考及来源，结合当前任务继续工作
```

### 2.1 主代理保留什么

- 基本职责、指令优先级、权限与安全边界、如实报告等核心要求。
- 记忆能力的最小发现锚点和调用约定：何时值得查、提供什么、如何使用返回参考。
- 当前任务目标、明确约束及用户刚提出的纠正；这些信息不能只依赖历史检索重新命中。
- 少数关键节点的提醒，目前明确讨论的是最终汇报前核对表达要求。

主代理不需要加载记忆代理的完整检索操作说明，也不需要知道其内部怎样逐层找目录、挑选正文。

### 2.2 记忆代理负责什么

- 根据问题与必要背景查找已有记忆。
- 阅读相关内容，核对来源、适用范围及可能的冲突。
- 返回当前有用的参考、必要出处和不确定性；没有找到时明确说明。
- 保留内部探索轨迹，不把目录清单、无关候选及全部试错过程回传。

“命中”不等于正确或适用。检索结果是参考，不能凭历史记录覆盖当前高优先级指令，也不能把历史许可变成永久授权。

## 3. 查询时机：模型自主判断，少数节点固定提醒

不以 Todo 的一级或二级边界强制触发查询，不要求每个步骤都查询。

核心判断是：

> 当前行动是否可能依赖用户要求、历史决策或已有经验？当前上下文是否已经提供足够且仍然适用的信息？

- 信息足够且仍适用：沿用，不重复查询。
- 存在具体信息缺口：针对缺口查询。
- 新事实改变原来的问题，或现有方法不足以继续：定向补查。
- 最终汇报前：核对当前有效的表达要求，即使模型本来就会写汇报。

这不是“只有不会做才查”。模型可能熟悉通用做法，却不知道本项目或用户的特定约定。也不是“每个新任务必须固定查一次”；查询粒度和时机仍由问题需要决定。

### 示例：一份要求可以跨多个步骤使用

开始任务时已查到“保持旧接口兼容，新增行为要补测试”。该要求可用于后续修改和验证，无需因为切换了 Todo 子项再次查询。

执行中发现一个特殊兼容分支，尚不清楚当初保留它的原因，则可以针对该分支查询历史决策。这个问题可以很小，不必对应完整工作单元。

### 常驻行为约定的示意文本

> 当前行动可能依赖用户偏好、历史决策或已有经验，而上下文中的信息不足时，主动查询记忆。已取得且仍适用的信息直接沿用；出现新问题时定向补查。最终汇报前，核对当前有效的汇报要求。

以上仅表达原则，不是最终系统提示词。单靠提示词不能保证模型永不遗漏；不为此重新引入完整的强制检索工作流。

## 4. 系统提示词精简与 skill 的位置

### 4.1 精简的是常驻细则，不是取消要求

表达偏好、项目惯例、专用方法、历史经验等可以按需取得，不必全部常驻。基本边界及必须可靠执行的规则不能简单降格为“也许能检索到的记忆”。

常驻上下文减少，并不自动保证总 token 或延迟减少；查询成本、结果长度和已有参考的复用仍需后续验证。

### 4.2 skill 是渐进加载的载体，不必全量注入

skill 的详细内容可以保留在外部，必要时加载。后台需要足够的可发现信息，例如适用场景和前置条件，但不要求把所有 skill 的名称、简介或全文一起注入主会话。

模型可按任务描述寻找方法，不应必须先猜中 skill 名称才有资格查询。skill 本身不是额外授权。

### 4.3 本期记忆 skill 不放在主代理侧

本轮澄清后的分工不是“主代理先加载 memory skill，再学习如何启动和执行检索”。

两个可选位置都在记忆代理内部：

1. 记忆代理加载检索 skill，按其中流程执行。
2. 检索流程直接写入记忆查询代理的专用系统提示词。

一期优先采用第二种：专职查询 Pi 每次都需要同一套流程，直接写入系统提示词更简单，不必额外增加 skill 加载步骤。以后存在多种按需检索策略时，再考虑拆成 skill。两种方式都应保持主代理不承载检索细节。

## 5. 一期方向：独立 Pi 直接检索，暂不接 Jev/Laya

一期优先跑通：

1. 主代理判断需要参考，并给出明确问题和必要背景。
2. 独立记忆 Pi 按专用提示词直接探索索引、读取相关内容。
3. 返回精简、有来源且说明适用性的参考。
4. 主代理结合当前要求继续工作。

暂不接入 Jev/Laya，不以复杂缓存、批量预取或 Todo 查询调度为前提。

这与背景文档中“记忆 Pi 小范围探索”的思路相容，但本记录没有核实任何现有代码或运行时能力。调用通道及生命周期仍需继续讨论，不能宣称已经实现。

后续若接入 Laya/Jev，可将选方向、选候选作为记忆代理内部优化，不要求主代理了解内部排序组件；排序也不替代适用性判断。

本期讨论聚焦查询链路。记忆写入、纠正沉淀及后台学习仍是相关问题，但跑通查询不等于已经具备自动学习能力，本记录不替它们定实现方案。

## 6. 当前要求与历史记忆如何相处

- 当前用户明确表达的要求直接生效，不必等后台长期记忆整理。
- 记忆代理不天然拥有主会话全部信息；当前纠正需要随请求提供，或经明确的数据通道取得，方式待定。
- “这次不要图”只作用于本次，不自动变为永久偏好。
- “以后汇报都先讲结论”表达长期意图，但长期保存与更新的具体机制尚未确定。
- 冲突先遵守指令层级，再判断适用范围及明确更新关系，不能仅凭时间新旧决定。
- 不能把助手自述成功、未执行计划或同一来源的重复转述当作独立成功证据。

### 示例：长程任务的最终汇报

已有长期偏好为“简洁，复杂关系可画图”。用户中途明确说“这次别画图，只说改动和验证”。

交付前，主代理提交汇报问题及本次要求。记忆代理取得相关历史参考，整理出“简短、说明改动和验证、本次不画图”，并保留必要来源。

主代理据此组织答案，不需要重读全部历史，也不应让旧偏好覆盖本次纠正。

## 7. 已讨论但本期不采用或不作为前提的方案

| 方案 | 当前结论 | 原因 |
|---|---|---|
| 每个 Todo 二级单元开始前强制查询 | 不采用 | 工作拆分边界不等于记忆需求边界，已有参考可能覆盖多个单元 |
| 规划时为全部单元固定问题并批量预取 | 不作为一期机制 | 问题与依赖事实会演变，增加调度和维护负担，不能覆盖所有细粒度问题 |
| 只在模型不会做时查询 | 不采用 | 熟悉通用方法不代表掌握用户偏好或项目约定 |
| 主代理先加载完整 memory skill | 不采用当前分工 | 主代理只需调用约定，检索细节归记忆代理 |
| 一期接齐 Jev/Laya | 暂不采用 | 先验证独立 Pi 检索及精简返回的使用闭环 |
| 把所有工具说明放进一个巨大统一入口 | 不作为解决办法 | 工具数量减少不等于常驻上下文减少 |

### 缓存讨论的保留结论

缓存可以是后台透明优化，而不是驱动模型工作方式的机制。本期不固定 hash 字段、全量预取策略或固定问题与 Todo 的绑定关系。

此前讨论过保存问题原文、通过查询标识复用请求、区分执行中请求与已完成结果。这些可留作后续选项，但相同原话不保证答案仍适用：项目、事实或用户纠正变化时，旧结果可能过期。不能为了命中缓存忽略新要求，也不要求模型记住并逐字重述旧问题。

## 8. 下一步待讨论细节

以下尚未定案，不应提前作为实现要求：

1. **主代理的最小提示词**：具体触发措辞、少数固定提醒及最小调用说明。
2. **记忆代理专用提示词**：可读范围、检索策略、探索预算、终止条件及无命中处理。
3. **查询输入**：问题之外最少需要哪些背景；当前任务要求及纠正如何传递。
4. **输出形式**：摘要长度、来源表达、适用范围、冲突及不确定性如何呈现。
5. **调用生命周期**：复用何种入口；同步或非阻塞返回；完成通知、结果获取、取消及失败如何处理。背景文档的 query/id 模式是参考，不在此直接冻结为一期接口。
6. **记忆更新**：已有记忆的来源、当前要求及时可见的方式，以及查询与后台学习的分工。
7. **验证方式**：用何种代表性任务检验主动查询、参考有效性、主会话轨迹减少和真实成本。
8. **后续优化顺序**：是否以及何时引入缓存、skill 拆分与 Jev/Laya，根据一期观察再决定。

## 9. 结论

> 主代理系统提示词只保留何时、如何咨询记忆的最小约定；详细检索流程放进专用记忆 Pi 的系统提示词。查询由模型按实际信息需要发起，少数关键节点提醒，不绑定 Todo 工作流。一期不接 Jev/Laya，先验证独立检索与精简参考返回。

本记录固化讨论方向，保留未决细节；没有修改系统提示词、工具、skill 或任何运行时代码。
