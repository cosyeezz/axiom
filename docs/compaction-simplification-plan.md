# 压缩机制简化方案与新会话交接

> 日期：2026-09-21
>
> 状态：讨论稿，尚未实施、尚未通过真实验收。
>
> 本文是下一会话的讨论起点，不是要求立即实现的指令。用户要求先收敛方案，再新开会话讨论。

## 1. 结论与范围

把压缩恢复为：

**独立完整原文档案 + Pi 原生压缩基座 + 非阻塞标题／概述 + 简单 facts 精确核验 + 一次可观察的原生回退。**

不再以复杂 JSON 任务状态协议作为压缩成功的前提。不继续为八类状态、稳定 ID、状态转换和授权迁移构建更多补丁。

此前“逐项实施审查文档全部优化”的计划，应按本方案重新评估：属于不再采用的复杂架构的优化，不继续照单实施。这一调整需要在新会话确认。

本阶段目标是可靠完成长对话压缩，保留原文可查与必要信息；不是建设完整任务状态数据库，也不是证明摘要语义绝对正确。

## 2. 用户实际需求

0. 独立保留全部未经摘要的原始会话内容，持续追加新增内容。
1. 以 Pi 原生摘要／压缩机制为基础，不另造一套替代流程。
2. 标题、概述等增强项不应阻断压缩。
3. 提供简单 facts 数组，摘要正文可以引用这些证据。
4. 程序在完整原文档案中逐条精确匹配 facts，全部匹配才标记为已核验。
5. 增强压缩异常时，允许一次不带增强要求的原生压缩回退，优先保障可用；但回退不能成为日常默认路径。

## 3. 当前事实与问题

### 已确认

- 当前生产流程不只是原生摘要加 facts，而是：结构化 JSON 状态生成、字段校验、来源补全、状态继承、约束授权检查、累计来源清单拼接、自定义预算检查及提交。
- 真实失败曾包括：无法找到切点、JSON 语法错误、字段类型错误、引文不匹配。
- 主分支曾合入 `2a47f85`（大工具结果切点回退）及 `816c7a2`（省略空字段兼容）。这些局部修复没有恢复完整可用性。
- 未合并实验尝试格式重试、严格工具输出和能力探测。少量历史曾生成成功，但完整历史副本未成功应用；没有连续两轮压缩成功的证据。
- 原生压缩也可能遇到网络、模型、窗口或取消问题，不承诺“永不失败”。本方案旨在消除增强功能引入的不必要失败门槛。

### 纠正此前方向

不能将“单测通过”“严格参数被服务端接受”“一次摘要生成成功”当作当前会话压缩可用的证明。

未合并实验中曾加入 `quote:null`、`verified_reference`、专用提交工具等机制；它们不是本方案的必选基础，不应因已有代码而继续保留复杂度。

## 4. 数据分离：档案不压缩，上下文可压缩

### 4.1 完整原文档案

- 按稳定消息／条目 ID 增量追加，确保幂等，不重复归档。
- 保存原始用户消息、助手消息、工具调用与结果，以及附件／图片的可恢复内容或持久引用。
- 生成的摘要单独保存，不作为原文再次混入证据语料；不能用新摘要替换旧原始消息。
- 分支、撤回等关系保留，不把不同历史路径混成一段无来源文本。
- 提供确定性的文本投影供匹配：每段对应原消息 ID，正文不改写。非文本附件不伪装成可逐字匹配文本。
- 优先复用已存在的 journal、raw archive、history_read/history_search；不再平行复制一套档案系统。

“去掉前一次摘要后追加”的意图，是不把生成摘要重复收录进原文档案。实现优先使用 ID 去重及追加，而非每次删改整份文件。

### 4.2 模型工作上下文

由原生压缩维护累计交接摘要与近期保留原文。前一次摘要用于生成下一份累计摘要，而不是要求只总结增量后直接替换所有旧记忆。

区分：
- 输入正文可以是增量历史，并结合前次摘要；
- 替换进上下文的正文仍须是完整累计交接信息；
- 展示用“本次概述”可以只概括新增进展。

### 4.3 摘要记录

记录正文、可选标题／概述、facts 及程序匹配位置、覆盖范围、所用模式和失败原因。完整来源索引留在持久层，正文只保留小型历史读取入口，避免越压越大。

## 5. 原生流程上的最小扩展

### 5.1 基座职责

原生能力负责合法切点、近期 tokens 保留、累计摘要上下文、生成和压缩记录应用。优先通过受支持的扩展点增强，不复制一套摘要控制器。

实施前必须验证当前安装 SDK 的实际扩展方式，尤其：如何拿到候选、如何在提交前校验、如何调用不递归触发增强的原生回退。当前尚未证明具体 API 接线，不在方案中把假设写成已支持。

如果原生接口不能直接提供“提交前候选校验”，先提出最小适配方案并讨论，不为硬套设计修改 SDK 私有内部状态。

### 5.2 输出要求

概念结构如下（不是规定必须输出严格 JSON 包装）：

```text
正文：完整交接摘要
可选标题：便于展示
可选概述：本次压缩新增进展
facts：短的、连续的原文摘录
```

- 正文沿用原生摘要能力，不要求八类数组、状态 ID、来源哈希或迁移状态。
- 标题／概述是展示数据，缺失、过长、格式不合规只影响展示；默认标题或不展示即可。
- facts 可采用隔离区块中的数组；具体格式在新会话确认，优先复用已有解析能力。
- 不用正则从任意残缺输出中猜一份合法对象，不补齐截断正文。
- facts 的编号、命中消息 ID 与范围由程序管理，不要求模型生成复杂来源对象。

## 6. facts 校验契约

1. 档案先覆盖本轮全部待压缩原文并确认可读。
2. 对 facts 每一项做精确匹配；匹配语料是完整原文档案中属于当前会话历史路径的确定性文本投影，不是只匹配头尾截取的摘要输入。
3. 每项必须在连续原文片段内命中，不能跨消息拼接凑成证据。
4. 程序记录匹配位置；相同引文存在多处时保留候选位置，不随意声称唯一来源。
5. 全部 facts 命中，才能标记“facts 已核验”。正文显式引用的 fact 编号也必须存在。
6. 任一非空 fact 不匹配，增强候选不作为已核验摘要提交；不能删除坏项、改写引文或清空 facts 后直接放行。

### 能力边界

精确匹配证明“这段话确实出现在原文”，不证明它客观为真、不证明摘要推理正确，也不证明重要约束没有遗漏。

旧历史引文不是新的用户指令或授权。保真依靠合理的原生摘要提示及任务续接验收，不再新增一套复杂状态授权协议。

### 待确认的小规则

- facts 建议取少量短证据，而不是逐句为摘要作证明；初始条数／长度不先拍脑袋定死。
- 缺失 facts、空数组和无法解析 facts 是否一律视为增强失败？建议有实质历史时如此处理，避免以空数组获得“核验通过”。
- 初期建议逐字匹配，不做模糊匹配；如需兼容换行差异，只允许明确、可逆的文本投影规则。

## 7. 正常路径与一次原生回退

```text
冻结待压缩范围，确认原文已归档
             ↓
使用原生流程生成增强候选
             ↓
正文有效 + facts 全部命中？
       ├─ 是：应用增强摘要
       └─ 否：丢弃增强候选，记录失败阶段
                         ↓
             最多一次纯原生压缩
                 ├─ 成功：应用并标记原生回退
                 └─ 失败：原文不变，明确报告
```

### 允许回退

- 增强格式、facts 缺失／解析／核验失败。
- 增强生成失败是否包含供应商瞬态错误：建议同样最多一次，但需避免在限流时立即重复请求；具体错误分类在接线时确认。

### 不得通过回退绕过

- 用户取消或强制停止。
- 原文归档失败、覆盖不完整。
- 原生不允许压缩、没有合法切点。
- 分支已变化、候选已过期而未重新取得合法快照。
- 提交失败或提交结果不确定。

### 回退必须满足

- 原生回退不带标题、facts、任务状态 schema 等增强指令，也不再次进入增强钩子。
- 不重新使用已经核验失败的候选正文。
- 总体次数有界，避免“失败→回退→增强→再回退”的递归。
- 明确展示本次模式与原因：原生回退不具有 facts 核验保证。
- 正常增强路径与回退分别计数。持续回退视为增强功能故障，不能用总成功率掩盖。

## 8. 预算收敛

用户关心的主要参数是原生近期原文保留 tokens。不要将它与模型实际窗口、输出上限混为一谈。

- 优先沿用原生切点和窗口处理。
- 不在原生压缩能够执行前，用另一套估算预算提前阻止它。
- 标题、facts 等附加输入保持小而有界。
- 仍尊重供应商硬限制，不能通过删除本地检查承诺任意长度输入都有效。
- 当前额外的 start/target/hard、摘要输入头尾分配等机制，逐项确认是否已由原生覆盖；重复部分移除，不以预算系统重构作为恢复可用的前置工程。

自定义预算在本轮修复之前已存在；具体引入提交尚未追溯。若讨论需要，另做 Git 历史核查，不能猜测来源。

## 9. 迁移与旧实验处理

- 不删除用户原文、既有压缩记录或历史索引。
- 老的结构化摘要作为历史记录兼容读取，不要求新摘要继续生成相同协议。
- 审视 `2a47f85` 与 `816c7a2` 是否仍处于有效路径：只在确认原生覆盖后移除冗余逻辑，不机械回滚。
- 未合并实验工作树：`../worktrees/Axiom-compaction-json-retry`，分支 `feat/compaction-json-retry`。保留现场供参考，不直接整体合并；其中本机验收脚本含本机路径，不作为通用交付脚本。
- 该工作树的 `docs/compaction-delivery-status.md` 记录旧路线状态；后续设计以本方案讨论结论为准。
- 参考审查文档：`docs/axiom-compaction-audit-and-optimization-2026-09-21.md`。此前它是主工作目录中的未跟踪用户文件，不应假定已在远端；跨机器交接需单独提供。

## 10. 实施顺序与停止条件

### 阶段一：验证原生基座

在隔离副本中调用真正的原生压缩，不附加增强条件；验证当前模型／接口是否能完成生成、应用和重新打开。失败则先报告原生错误，不能继续叠加增强掩盖。

### 阶段二：原文档案与轻量增强

确认原文可恢复、匹配投影一致，再接入非阻塞标题／概述与 facts。增强必须在提交前完成核验。

### 阶段三：异常回退

故障注入验证最多一次原生回退、无递归、取消不重发、数据安全错误不绕过。

### 阶段四：真实连续压缩与上线

完整当前历史副本至少连续压缩两轮，确认旧要求可续接、原文可查、记录可持久恢复。自动和手动入口应使用同一基本流程。

通过后才按项目规则提交、同步、合并和推送；真实模型请求明确设次数／费用边界，不重复无限试错。不擅自重启正在进行的真实会话服务。

## 11. 最小验收清单

- [ ] 原生压缩在完整历史副本成功应用，而非仅生成成功。
- [ ] 原文消息、工具配对与附件仍可恢复，重复归档不重复写入。
- [ ] 标题／概述故障不影响正文应用。
- [ ] facts 正确时全部定位；不存在的、拼接的、改写的引文不通过。
- [ ] facts 缺失／失败时只进行一次原生回退，并明确标记无核验保证。
- [ ] 原生也失败时原文不变；取消、归档故障和提交不确定不绕过。
- [ ] 两次连续压缩后，前次关键约束与未完成工作仍能用于继续任务。
- [ ] 重新打开会话后摘要、覆盖关系及原文入口可恢复。
- [ ] 自动触发、手动同步、手动异步行为一致，未新增后台占位死锁。
- [ ] 单测、故障注入、真实请求分别报告；增强成功率与回退率分别报告。

## 12. 新会话先讨论这四个问题

1. 是否确认用本简化方案替代“先实现所有架构优化”的旧路线？
2. facts 是少量关键证据，还是要求摘要每条重要结论都引用？建议前者，避免再次变成复杂证明协议。
3. 是否采用“增强失败→一次纯原生回退”的默认异常策略，并接受该次没有 facts 核验保证？
4. 原生接口接线验证后，哪些现有预算／后台控制器确属重复，哪些需要暂留以兼容手动异步体验？
