## 结论

- 存储/启动 **6/6** 硬门槛通过，计量自检 **6/6** 通过，两个同库锁实验通过，退出码 **0**。
- 大合成会话：原来每次约 **1.35MB** 的整份 SQL 绑定数据，拆表后各测试动作只绑定 **17–678B**。这不是数据库文件增量，也不是实际磁盘写放大。

## 方法与口径

```text
环境   AMD Ryzen 7 5800X / Windows 10.0.26200 x64 / Node v24.19.0
small  8 会话 × 4 摘要(200字符) × 2 任务(result 400字符 + prompt 1200字符)
large 16 会话 ×32 摘要(1000字符)× 6 任务(result 49152字符 + prompt 16384字符)
样本   small写40次、large写12次，每项读5次；单机单轮，无多轮聚合
```

- **写字节**：写语句全部字符串绑定参数的 UTF-8 字节数，包含 namespace/主键/WHERE 键；新旧同口径。读参数不计，store 层不重复计；数字绑定不计，因此不能叫总磁盘写入量。
- **SQL 次数**：语句执行次数；写 SQL 单列，不含事务控制和 DDL。新计量必须先装配，再创建缓存 prepared statement 的 SessionStore。
- **旧微基准**：复刻旧 persist 投影与 stringify→parse→set 管线，完整保存成本都在计时区间；不是端到端。任务进度使用真实单条快照，通知位每次切换，计时每次递增，避免同值空写夸大加速。
- **新微基准**：直接调用真实存储 API，标题/摘要/进度/通知/计时每次更新一个实体；“送达+修剪”只计这两个存储动作，不包含完整通知生命周期。
- **端到端**：真实 Sessions + fake SDK、合成填充数据，零模型网络；启动计时不含模块导入和种子数据建库，包含 load。首开另记，不能把首开成本消失算作启动加速。
- **分位数**：样本排序后最近秩；large仅12次，p95/p99相同并不意味着尾延迟稳定。
- **事件循环**：同步阶段前后确实让出定时器采样；存储阶段最大漂移近似整批同步阻塞，Windows定时器还有粒度误差，不是每次保存的阻塞值。
- **RSS/WAL**：RSS在测量结束、清理前采样，非启动瞬时峰值，受GC影响；WAL受自动checkpoint和复用影响，不等于绑定字节，不能拿其增长线性推导锁窗口。

## 硬门槛及锁实验

1. 新增摘要：旧任务行逐字节不变，任务UPDATE触发器禁止改写，写SQL恰1条。
2. 通知位：从false改true，小/大任务都仅25B，写SQL各1条，不能随runtime/result体积扩大。
3. 改标题：任务/摘要/事件行不变，三表UPDATE触发器禁止改写，写SQL恰1条。
4. 逐token：真实Sessions订阅注入100个消息开始/增量/runtime事件，观察窗口SQL总数0；无token列或不允许的计数内容。任务runtime用量及压缩详情仍按计划保留。
5. 待通知查询：false/缺键入选，true不入选。
6. 懒启动：无待通知SDK=0，一个待通知会话SDK=1。

历史独立回归：256消息、256重试与256压缩记录，以getter/toJSON次数限制完整扫描；修复前消息被读65,664次，修后通过上限且消息ID/重试边界/压缩结果保持正确。不是凭一次耗时猜复杂度。

锁实验先让victim连接就绪，再由holder拿写锁并发READY，父进程通知victim开始写，排除Node启动/模块导入的时间；**busy_timeout仍5000，原断言未放宽**：

| holder持锁 | victim结果 |
|---|---|
| 300ms | 等328.3ms成功，exit 0 |
| 6000ms | 等5561.7ms后database is locked，exit 2（预期锁超时） |

## 限制

这是合成数据和fake SDK验收，不是正式会话、真实模型或全服务启动基准；不承诺跨机器速度。拆表减少热路径绑定负载，但SQLite仍为单写者，同步SQL仍能阻塞事件循环。未测按写入字节分级的锁窗口，不据两次锁实验声称锁时间按比例缩短。不加入Worker、缓存或分库；只有真实运行仍出现可复现卡顿时再评估。
